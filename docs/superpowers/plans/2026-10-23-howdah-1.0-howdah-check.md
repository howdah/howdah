# Howdah 1.0 — full `howdah-check` Implementation Plan

> Infra/tooling sub-plan of the 1.0 build. Lighter execution (one implementer + one independent review). `howdah-check` is a version-independent POSIX-sh script.

**Goal:** complete `howdah-check` for 1.0 by making `detect` **architecture-aware and directly actionable** — report the machine arch and, for each detected PHP install, name the exact release tarball that matches it — closing the install-UX gap created now that Howdah ships both x86_64 and aarch64 builds.

**Architecture:** the 0.1 `tools/howdah-check` (POSIX sh, ~418 lines) already finds every PHP install (PATH + Surý/Remi/cPanel/Plesk/CloudLinux layouts) and reports version, Zend API, NTS/ZTS, extension_dir, SAPIs present, and whether Howdah is loaded in each — plus `web <url>` sends the two harmless self-test requests (selftest marker + an over-part-limit multipart). This sub-plan adds arch detection + per-install artifact guidance; it does not restructure the script.

**Spec:** `docs/superpowers/specs/2026-10-22-howdah-design.md` §8 (install/verify; `howdah-check` is a hard requirement, read-only by default).

## Global Constraints
- **Version-independent & read-only:** no PHP version baked in; `detect` must not modify anything. POSIX sh (works on the old `/bin/sh` of CentOS 7 / Ubuntu 14.04). The script also rides inside every release tarball and ships as a standalone asset (see `packaging/build-release.sh`) — keep it a single self-contained file.
- **Arch values** must match the tarball naming from sub-plan 2: `x86_64` and `aarch64` (map `uname -m` `arm64`→`aarch64` if it ever appears).
- **No overclaiming:** the recommended asset names a pattern with the install's concrete selectors (minor, API, arch) and the release VERSION as a placeholder the user fills from the latest release — never a fabricated version/URL.

## Tasks

### Task 1: arch-aware detect + per-install artifact recommendation + tests
**Files:** `tools/howdah-check`; a test under `tools/` or `tests/` if a shell-test pattern exists (else a small self-contained check).
- Determine the host arch once (`uname -m`; normalize `arm64`→`aarch64`, anything else reported verbatim) and show it in `detect`'s output (header or per-install). A PHP extension `.so` must match the host arch, so this is host-wide.
- For each detected install that has a known Zend API and minor version, print a **"matching release asset"** line: `howdah-<VERSION>-php<minor>-<api>-linux-<arch>.tar.gz` (with `<VERSION>` shown as a literal placeholder to take from the latest GitHub release), plus a one-line pointer that `howdah-check` itself and the asset are on the releases page. Where API or minor is unknown (the config-only installs), say the asset can't be determined rather than guessing.
- Keep `web` unchanged in behavior (it already does the EICAR-style self-test). Only touch its help text if arch/asset wording needs it.
- Update the `usage()`/header comment to mention the arch/asset reporting.
- **Tests:** add a focused test that runs `howdah-check detect` in a controlled way (e.g. against a fake `ROOT`/PATH fixture the existing script already supports via `$ROOT`, or at minimum asserts the arch line appears and `howdah-check -h`/arg-parsing still works). Keep it POSIX and runnable without a real multi-PHP box. If no existing test harness, add a tiny `tools/howdah-check.test.sh` that exercises arg parsing + the arch/asset formatting via a stubbed install, and document how to run it.
- Verify the script still passes `sh -n` (syntax) and, if available, `shellcheck` with no new warnings; run it live (`howdah-check detect`) on this host and confirm the arch line + sane output.
- Commit.

## Review Focus
- POSIX-sh portability: no bashisms introduced (the script targets old `/bin/sh`); `sh -n` clean. → Task 1.
- The artifact recommendation must use the install's REAL api/minor/arch and must degrade gracefully (say "unknown") rather than print a wrong/guessed asset name for config-only installs. → Task 1.
- `detect` stays strictly read-only (no writes/network). → Task 1.
- `uname -m` normalization covers the arm64/aarch64 spelling so the recommendation matches the actual tarball names. → Task 1.
