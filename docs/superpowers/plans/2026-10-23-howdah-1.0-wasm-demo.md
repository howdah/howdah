# Howdah 1.0 — WebAssembly demo of the core Implementation Plan

> Sub-plan of the 1.0 build. The pure-Rust `howdah-core` compiled to WebAssembly so the website can show visitors what Howdah would decide for a chosen request — running the REAL core logic in their browser, never a server. Lighter execution (one implementer + one independent review). The polished multi-sample UI integration lives in the full-site sub-plan; this builds the wasm module, its JS glue, and a minimal standalone demo page proving it works.

**Goal:** a browser-loadable WebAssembly build of `howdah-core` plus the JS glue + a minimal demo page, where a visitor picks a sample request **shape** (a normal form; a defanged PHP2Shell-shaped part flood; a malformed multipart; an oversized filename) and sees Howdah's real verdict (Allow / Log / Block, the rule, the reason).

**Architecture:** a new `crates/howdah-wasm` crate (crate-type `cdylib`) depending on `howdah-core`, built for `wasm32-unknown-unknown` with **no wasm-bindgen** — it exports a few plain functions (`alloc`/`dealloc` + an `analyze`) and returns a JSON verdict through wasm linear memory, read by hand-written JS. It reuses the core's real decision pipeline (`Config::from_toml` → `MultipartState::feed` → `Limits::check` → `rules::decide`, i.e. the same path `ffi.rs` drives), so verdicts match the shipping extension. No PHP, no network, no payloads — the JS builds a benign body from the chosen structural sample (counts/sizes only), exactly like the lab corpus.

**Tech Stack:** Rust (`wasm32-unknown-unknown`, release), hand-written JS (`WebAssembly.instantiate` + linear-memory marshalling), a static HTML demo page, GitHub Actions (a wasm build check in `ci.yml`).

**Spec:** `docs/superpowers/specs/2026-10-22-howdah-design.md` §10 (Live demo: the Rust core compiled to WebAssembly; visitors pick a sample incl. a defanged PHP2Shell-shaped one described by its structure; demonstrates only checks whose logic lives in the core; never a copy-pasteable payload) and §9 (reproducer disclosure: shape only).

## Global Constraints
- **No payloads, shape only (design §9/§10):** samples are described by structure (part count, file count, header sizes, nesting depth). Any benign body the demo builds is counts/sizes only — never an exploit string or RCE chain, never copy-pasteable as an attack.
- **Faithful, no overclaiming:** the demo runs the actual `howdah-core` verdict path; it must not hard-code or fake a verdict. It demonstrates only checks whose logic is in the core. The page states that it runs the real core in-browser and is not a scanner of the visitor's own server.
- **No new heavy toolchain:** plain `cargo build --target wasm32-unknown-unknown --release` (no wasm-bindgen/wasm-pack). `howdah-wasm` must also compile on the host target (so the default `cargo build`/CI host job is unaffected) — i.e. no wasm-only crates (`wasm-bindgen`, `web-sys`, `js-sys`).
- `crates/howdah-core` is NOT modified (if the wasm crate needs a small helper, add it behind the existing public API; prefer reusing `ffi`-equivalent logic without touching it). Dual MIT/Apache-2.0.

## Tasks

### Task 1: `howdah-wasm` crate — core → wasm with a faithful `analyze`
**Files:** `crates/howdah-wasm/Cargo.toml`, `crates/howdah-wasm/src/lib.rs`; add to the workspace `members`.
- cdylib depending on `howdah-core`. Export (plain `#[no_mangle] extern "C"`, no bindgen):
  - `howdah_wasm_alloc(len: usize) -> *mut u8` and `howdah_wasm_free(ptr, len)` so JS can place input bytes in wasm memory.
  - `howdah_wasm_analyze(cfg_ptr, cfg_len, body_ptr, body_len) -> u64` (or an out-param pair): parse the config TOML (empty → safe defaults), run the real pipeline over the body bytes (begin → feed → end, reusing the same core calls `ffi.rs` makes), and produce a JSON verdict string `{"action":"allow|log|block","rule":"…"|null,"reason":"…"}`. Return the (ptr,len) of that JSON in wasm memory (e.g. pack into a u64, or write to two exported globals / an out buffer). Include matching `howdah_wasm_result_ptr/len` accessors if that's cleaner than packing.
- Keep all `unsafe` minimal and sound (valid-for-len, no leaks except the result buffer which JS frees via `howdah_wasm_free`). Panic-safe is nice-to-have (a panic in wasm just traps; guard if cheap).
- **Tests (host):** unit tests (run on the host target, where the crate also compiles) asserting `analyze` returns the right JSON for: a normal small body (allow), a part/file flood at default limits (block, `max_parts`/`max_files`), and a malformed body (the `malformed_multipart` rule). These prove the marshalling + verdict logic without a browser.
- Build for wasm: `cargo build -p howdah-wasm --target wasm32-unknown-unknown --release` → confirm a `.wasm` is produced and is reasonably small. Also confirm `cargo build -p howdah-wasm` (host) and `cargo test -p howdah-wasm` pass.
- Commit.

### Task 2: JS glue + minimal demo page + CI build
**Files:** `site/demo/howdah-wasm.js` (glue), `site/demo/index.html` (minimal standalone demo), a build step that copies the `.wasm` into `site/demo/` (a `packaging/build-wasm.sh` or a documented cargo invocation), and a wasm build job in `.github/workflows/ci.yml`.
- **JS glue** (`howdah-wasm.js`): instantiate the `.wasm`, expose an `analyze(configToml, bodyBytes) -> {action, rule, reason}` that marshals via `alloc`/memory/`analyze`/reads the JSON result/`free`. Pure vanilla JS, no framework, no network.
- **Demo page** (`index.html`): a small, accessible, no-tracker page with a sample picker — at least: (1) a normal upload form; (2) the **defanged PHP2Shell-shaped part flood** described by its structure (e.g. "~2,500 tiny parts"); (3) a malformed multipart; (4) an oversized filename. For each, JS builds a BENIGN body from the structural description (no payload), calls `analyze`, and shows the verdict (action + rule + reason) and a one-line explanation. Copy states plainly: runs the real Howdah core in your browser; nothing is sent anywhere; this is not scanning your server. Works without a build step beyond loading the `.wasm`.
- **CI:** add a `wasm build` job to `ci.yml` that installs the `wasm32-unknown-unknown` target and runs `cargo build -p howdah-wasm --target wasm32-unknown-unknown --release` (+ the host `cargo test -p howdah-wasm`), so wasm breakage is caught per-PR.
- Validate locally: build the wasm, serve `site/demo/` (e.g. `python3 -m http.server` or any static server) and, if a headless browser is available, confirm the page loads the wasm and the PHP2Shell sample shows **Block / max_parts**; otherwise exercise the glue via Node (`WebAssembly` is available in Node) with a small script asserting the same verdicts the Rust tests assert. Record whichever was used.
- Commit.

## Review Focus
- **Faithful verdicts:** `analyze` must route through the real `howdah-core` decision path (same as `ffi.rs`), not a reimplementation — a drift would make the demo lie. → Task 1.
- **wasm memory safety / leaks:** `alloc`/`free` pairing, `analyze`'s result buffer ownership, valid-for-len slices; no unsoundness and no unbounded leak per call. → Task 1.
- **No payload leakage:** no sample, body-builder, or copy string is a usable exploit; PHP2Shell sample is structural counts only. → Task 2.
- **Host build unaffected:** `howdah-wasm` compiles on the host target with no wasm-only deps, so the default workspace build/test and CI host job still pass. → Task 1.
- **No-network / no-tracker demo page:** the page makes zero third-party requests (matches the site's privacy bar). → Task 2.
